# Per-alarm start date and one-time future date

**Status:** completed

**Label decision:** the switching label — "Starts on" when weekdays are selected, "Date"
when none are.

## The issue

An alarm today can only be one of two things:

- **Recurring** — rings on the selected weekdays, starting immediately. There is no way to
  say "start this from 1 August"; if you set a weekday alarm for a course that begins next
  month, it rings every week until then.
- **Once** — rings at the next occurrence of that time, meaning today or tomorrow. There is
  no way to say "ring on 3 March at 07:00". A dentist appointment three weeks out cannot be
  set at all.

This is the last item from the original list that has not been addressed.

## Design

### One column covers both

Both needs are the same idea — *do not consider any day before this date* — so they share a
single field:

```kotlin
val startEpochDay: Long = 0L   // 0 = no start date, i.e. today's behaviour
```

Same UTC-midnight basis as `pauseStartMillis` and `skipNextEpochDay`, so the value can come
straight out of the Material date picker with no conversion.

What it means depends on whether the alarm repeats — and this falls out of the existing code
rather than needing a second flag:

| Repeat days | `startEpochDay` | Behaviour |
|---|---|---|
| set | 0 | unchanged: next selected weekday |
| set | a date | first selected weekday **on or after** that date |
| empty | 0 | unchanged: today or tomorrow, whichever is next |
| empty | a date | rings once on exactly that date — the "future one-time alarm" |

So "one-time future date" is not a new mode. It is a one-shot alarm that has been told which
day to land on.

### Scheduling

`nextTriggerTime()` gains one parameter, `startEpochDay`, and the rule goes into the existing
`isSkipped()` helper — a candidate day earlier than the start date is rejected:

```kotlin
val beforeStart = startEpochDay > 0L && day < startEpochDay
```

For the one-shot branch there is one extra step: instead of beginning at "today, or tomorrow
if the time has passed", begin at the start date when that date is in the future. Without
this the existing loop would walk forward a day at a time from today, which works but is
wasteful for a date months away, and the 366-day cap would break a date more than a year out.

The recurring branch needs no other change — its scan already advances until a day is
acceptable.

### After a dated one-shot fires

A one-shot alarm currently stays switched on in the list forever, because it simply never
re-arms. That is tolerable for "tomorrow", but a dated alarm that stays lit weeks after its
date looks broken.

So when a one-shot with a start date fires, `AlarmReceiver` will disable the row. This is the
only new database write on the firing path; it goes inside the `goAsync()` block that already
exists there for timers.

**This is the riskiest part of the plan** — the ring must never depend on the write. The write
happens after the foreground service has been handed the alarm, and any failure is logged and
swallowed. Worst case the row stays lit and the user turns it off by hand.

### A start date that has passed

Like `skipNextEpochDay`, a past value is naturally inert — no future candidate day can ever be
earlier than it. So nothing needs clearing. The UI treats a start date as "active" only while
it is today or later, and stops showing it afterwards.

### Interaction with what is already there

The pause window, skip-next and holiday rules all live in the same `isSkipped()` check and
compose without special cases: an alarm can start on 1 August, skip holidays, and be paused
for a week in September. The one combination worth a test is a start date landing inside the
pause window — the alarm should resume when the *later* of the two ends.

- `data/Models.kt` — `startEpochDay` column, plus `isStartDateActive()` and
  `hasFutureStartDate()` helpers matching the existing skip/pause ones.
- `data/AppDatabase.kt` — version 8 → 9, `MIGRATION_8_9` adding the column with default 0.
- `data/ScheduleTiming.kt` — `startEpochDay` parameter, the `beforeStart` rejection, and the
  one-shot start-day jump.
- `ui/AlarmScheduler.kt` — pass it to `nextTriggerTime`, carry `START_EPOCH_DAY` in the intent.
- `ui/Receivers.kt` — carry it through the re-arm; disable a dated one-shot after it fires.
- `ui/ClockViewModel.kt` — `startEpochDay` on `addAlarm`; a `setAlarmEnabled` style helper for
  the receiver's disable path if one is not already reachable.
- `AlarmsScreen.kt` — a "Starts on" row in the editor with a date picker and a Clear button;
  a badge on the alarm row while the date is still in the future; the "rings in X" toast
  already recomputes from `nextTriggerTime`, so it will follow automatically once the value
  is passed in.
- `data/BackupManager.kt` — the new column, defaulting to 0 for older files.
- `app/src/test/.../ScheduleTimingTest.kt` — tests for: recurring alarm skipping to the first
  selected weekday on or after the start date; dated one-shot landing exactly on its date; a
  past start date being inert; a start date more than a year out (the 366-day cap); and the
  start-date-inside-pause-window combination.

## Open question for you

**What should the editor call this?** The same field is doing two jobs, and the label changes
which one the user thinks they are getting:

- One row labelled **"Starts on"**, which reads naturally for a repeating alarm and is merely
  odd for a one-off ("starts on 3 March" for an alarm that only rings once).
- Or the label switches with the alarm type — **"Starts on"** when weekdays are selected,
  **"Date"** when none are. Clearer to read, slightly more code, and the label changes under
  the user as they toggle weekday chips.

I lean towards the second: the wording matching what the alarm actually does is worth the
small extra complexity, and someone setting a one-off dated alarm is the person most likely
to be confused by the wrong word.
