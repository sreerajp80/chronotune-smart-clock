# Per-alarm start date and one-time future date

Implements `plans/20260719_174120_alarm-start-date.md`.

## What this adds

One new setting on each alarm: **a date the alarm is not allowed to ring before.**

It does two jobs, decided by whether the alarm has repeat days:

- **With weekdays selected** — "don't begin yet". The alarm stays quiet until that date, then
  follows its normal weekly pattern. Labelled **Starts on**.
- **With no weekdays selected** — the alarm only rings once, and the date says which day.
  This is the future-dated one-time alarm. Labelled **Date**.

The label switches between the two as the user taps weekday chips, so the wording always
matches what the alarm will actually do (the option chosen at approval).

## Two things worth knowing

**Why one column covers both features.** Both needs are the same rule — *reject every day
before this date*. What differs is only how many days survive afterwards: a repeating alarm
has a weekly pattern to fall back on, a one-shot has exactly one day left, which is the date
itself. So no second field and no mode flag was needed, and the rule slots in beside the pause
window, skip-next and holiday checks that already share `isSkipped()`. They compose freely: an
alarm can start on 1 August, skip holidays, and be paused in September.

**The jump, not the walk.** The scan walks forward a day at a time and gives up after 366 days.
A start date further out than that would have silently failed, so when the start date is still
ahead the calendar is moved straight to it before scanning. This is also what pins a dated
one-shot to its own day. There are tests for a date 500 days out in both shapes.

## The risky part, and how it was contained

A dated one-shot switches itself off after ringing — otherwise it would sit in the list looking
armed weeks after its date. That is a database write on the alarm firing path, the most
sensitive path in the app.

It is placed *after* the ring has been handed to the foreground service, runs inside the
`goAsync()` block already used there, and swallows any failure with a log line. If the write
fails the alarm has still rung correctly and the row simply stays lit for the user to switch
off by hand. A snoozed re-ring is unaffected: the temporary snooze alarm carries no start date,
so it never takes this path.
